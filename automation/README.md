# Toward autonomous applications — implementation and evidence

Updated September 12, 2026. **Implemented: read-only audit and discovery. Not implemented: application submission. No applications have been sent.**

## Run without interactive input

```sh
python -m unittest discover -s tests -v
python -m automation.audit --live
```

Python 3.11+; no packages, credentials, configuration, or profile re-entry required. The existing job list and profile are the inputs. Output: `assets/verification/autonomy-report.html` and `.json`. Omitting `--live` produces an explicitly offline report (and overwrites the output); use `--output /tmp/offline-audit` to keep a live snapshot intact.

The workflow `.github/workflows/autonomy-audit.yml` runs the audit on branch pushes and daily once installed on the repository's default branch. It uploads reports as workflow artifacts, **not** to GitHub Pages. It cannot run periodically just because a file exists on this working branch; it is not deployed or active yet. The committed HTML is a snapshot, not a live service.

## What now happens automatically

1. Read all 120 legacy entries; retain a row for every ID, with source and apply links, HTTP status, and explicit irregularities.
2. Traverse every existing profile leaf; record its JSON path and provenance problem, without copying personal values into the report.
3. Fetch unique employer/apply URLs with bounded concurrency, timeouts, response size, HTTPS validation, and redirect validation. No POSTs, logins, CAPTCHA solving, or anti-bot workarounds.
4. Extract Greenhouse, Lever, and Ashby board links from employer pages. Also check legacy ATS board tokens, but flag their employer relationship when no employer link was retrieved.
5. Fetch published listings using documented public APIs. Preserve endpoint URL, timestamp, SHA-256 of response bytes, stable platform/board/requisition key, title, location, and skill excerpts. Full responses are not retained, so hashes establish snapshot identity, not a locally reproducible archive.
6. Exclude Greenhouse prospect posts and Ashby unlisted jobs; deduplicate listings by stable key within each run.
7. Triage using transparent chemistry-skill keyword overlap, not invented match percentages. Distinguish San Francisco from South San Francisco. Remote eligibility and actual public-transit routes remain unknown. Keyword overlap does **not** prove qualifications; all discovered jobs remain blocked.
8. Publish a readable report and machine-readable queue. Record failed checks as unknown, **never closed**. There is no application submission ledger or cross-run application deduplication because there is no submitter yet.

## Findings from this run

The standalone Python process encountered TLS/SSL EOF errors fetching source pages and APIs in this sandbox. The saved automated report truthfully records those errors and zero retrieved API listings. This is **not** evidence that no matching jobs exist. The API parsing/discovery path is covered with mocked tests, not a successful live end-to-end API test here.

The separate web retrieval tool could read official documentation and several employer pages. These observations are recorded separately in [official-source-review.md](official-source-review.md); they are not passed off as successful Python checks. This is a row-by-row **audit of verification gaps**, not a claim that every job, skill, date, qualification, and commute was independently verified.

## Official sources and realistic submission options

| Method | Verified documentation | Practical conclusion |
|---|---|---|
| Greenhouse public discovery | https://docs.greenhouse.io/job-board.html#list-jobs | Public GET listing API; implemented. |
| Greenhouse submission | https://docs.greenhouse.io/job-board.html#authentication | Application POST requires a Job Board API key / Basic Auth. An applicant's permission does not supply an employer integration key. Not implemented. |
| Lever public discovery | https://github.com/lever/postings-api#get-a-list-of-job-postings | Public GET listing API; implemented for global instance. |
| Lever submission | https://github.com/lever/postings-api#apply-to-a-job-posting | POST requires a key generated by an account Super Admin; required form fields are employer-configurable, and POST is rate-limited. Not an unrestricted applicant submission endpoint. Not implemented. |
| Ashby public discovery | https://developers.ashbyhq.com/docs/public-job-posting-api | Published job data and hosted application URLs; implemented. This document is not evidence of unauthenticated application submission permission. |
| Hosted employer forms | Employer's actual application page | Next viable route: per-platform browser adapters in a private runtime, after checking platform rules, form requirements, and session access. Not implemented or claimed universally supported. |
| Email applications | Explicit employer instructions on a verified posting | Only if the employer explicitly accepts this method, to its published recruiting address. Do not guess addresses or mass-email recruiters. Not implemented. |

## Highest-priority upgrades still needed

1. **Recover primary candidate evidence from already available private documents.** Current checkout has generated profile/documents, not provenance proving every answer. Last name is blank. Do not derive a legal name from an email address. Work authorization, sponsorship, driver's license, veteran/disability answers, notice period, salary, and publication authorship need their own evidence. Absence of a skill in a resume means unknown, not necessarily “No.” Existing kits and screening files are legacy drafts and must not be submitted automatically.
2. **Private runtime, not GitHub Pages.** Keep candidate identity, resume, sessions, receipts, and credentials outside public Git and public build artifacts. Existing repository already contains contact data and profile copies in kits/extensions; this change does not remove historical exposure. Never put employer keys into frontend JavaScript. The DNS checks in this audit are defense-in-depth, not a hardened untrusted-URL service; use network-level egress restrictions before exposing it to arbitrary inputs.
3. **Fresh requisition and full requirements checks.** Fetch exact job descriptions/forms, verify employer-to-ATS ownership chain, deadline, location, work schedule, compensation where required, degrees, licenses, experience, and every mandatory screening field. Preserve clause-level quotes and original evidence. A general board or address is not a vacancy. Recheck immediately before submission.
4. **Adapter-by-adapter permitted submission.** Start with an official hosted application form that can be completed from verified facts without login/consent ambiguities. Fill and upload only the necessary information. Stop on unknown required fields, missing primary evidence, CAPTCHA, MFA, application fees, unclear consent, and site restrictions. Queue other jobs without blocking the entire run. The user's general request to apply does not resolve unknown factual answers.
5. **Transactional submission ledger before enabling sends.** Reserve a unique employer/requisition/candidate key under a database uniqueness constraint; persist intent before sending; save a real confirmation ID/receipt. A timeout after sending becomes `submission_unknown` requiring reconciliation, not a blind retry. Add rate limits, daily caps, kill switch, and receipt retention. Do not claim submission merely because a button was clicked or HTTP 200 returned.
6. **Exception-only reporting and continuous discovery.** Re-run supported sources, flag stale listings and unsupported ATS platforms, and provide evidence-linked review queues. No manual task is required for this audit, but a genuinely mandatory unknown identity fact cannot be solved by automation alone.

The achievable goal is **automatically submit eligible, fully evidenced applications on supported, permitted channels; automatically quarantine everything else**. “All jobs, zero exceptions” is not a truthful promise with the current information or platform constraints.
